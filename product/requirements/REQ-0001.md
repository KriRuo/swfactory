## Reasoning

This requirement operationalizes USECASE-0001 (Find a Note in a Growing
List), which in turn traces to EVID-0001's stakeholder complaint that
notes become unfindable past a screenful.

I chose keyword search over title/body as the minimum mechanism because
it's the smallest capability that directly resolves the reported failure
("can't find") without presuming a richer information architecture
(folders, tags, pinning) that the evidence doesn't support. Those remain
reasonable follow-on requirements but shouldn't be bundled into this one
without separate evidence of demand.

Priority is set to **must**: the evidence describes a currently broken
core workflow (retrieving one's own previously created content), not a
nice-to-have enhancement — once the list exceeds one screenful, the
product's basic note-keeping value proposition breaks down.

Left open for the Architecture/Planning stage: whether search should be
substring/full-text, live-as-you-type, and what "screenful" threshold (if
any) should trigger surfacing the search UI. Flagged `pending` for human
approval before downstream design work begins, per the L2 governance
gate on requirements.
